WhatsApp AI Ops Agent — Hackathon Architecture Plan
Project codename: FieldBot
Target: 2–3 minute demo video for hackathon submission
Build window: 4 days
Core premise: An AI agent that lives in WhatsApp and autonomously runs two high-value solar operations workflows — site progress inspection and material procurement — end to end, without the operator ever opening a browser.

1. End Goal
The finished product demonstrates two sequential acts in a single continuous demo:

Act 1 — Site Inspection to Invoice (0:25–1:30)
A site supervisor sends 3 rooftop photos to a WhatsApp number. The AI agent analyzes the photos using a vision LLM, counts installed panels, flags any visible issues, calculates percentage completion, and automatically creates both a structured inspection report and a progress claim invoice draft — all within 90 seconds. The portal dashboard reflects these new records in real time.

Act 2 — Procurement Request to PO (1:30–2:45)
The project manager sends a natural language WhatsApp message requesting materials. The agent parses the request, queries approved vendors filtered by region, simulates an RFQ dispatch, generates a realistic quote after a short delay, presents the quote for one-word approval, and on confirmation creates a Purchase Order in the portal. Total elapsed time: under 4 minutes.

The demo video format: a BEFORE segment showing manual chaos (WhatsApp message threads, spreadsheets, 3-day delays), then the live agent demo, then a side-by-side closing with hard numbers.

3. Tech Stack
Layer	Choice	Reason
Backend	Python, FastAPI	Fast to write, async-native, SSE built-in
Database	PostgreSQL	Via Supabase free tier for zero-ops setup
ORM	SQLAlchemy 2.0 (async) or Tortoise ORM	Developer preference
Frontend	React + Vite + TypeScript	Fast dev server, easy deploy
Styling	Tailwind CSS	Rapid UI
Real-time	Server-Sent Events (SSE)	Simpler than WebSockets for one-way push
WhatsApp	Twilio WhatsApp Sandbox	Free, no business approval required
LLM	[LLM_PROVIDER] — to be decided by developer	Two usages: vision (photo analysis) + text (intent extraction, quote generation)
Backend hosting	Railway or Render (free tier)	Needs a public HTTPS URL for Twilio webhook
Frontend hosting	Vercel	Free, instant deploys
Image storage	Cloudinary free tier or keep Twilio media URLs	Inspection report photos need a permanent URL

5. Backend API Specification
WhatsApp Webhook

POST /webhook/whatsapp
Receives Twilio's POST payload. Twilio sends From (phone number), Body (message text), and MediaUrl0/MediaContentType0 for any attached media. This is the single entry point for all agent logic. Returns TwiML <Response> (can be empty; replies are sent via Twilio REST API, not TwiML response).

Projects

GET  /projects              → list all projects
GET  /projects/{id}         → single project with related counts
Inspection Reports

GET  /inspections                   → list all, newest first
GET  /inspections/{id}              → single report with photo URLs + issues
POST /inspections                   → internal — called by agent only
     Body: project_id, photo_urls, panels_detected, panels_with_issues,
           issues, completion_pct, ai_analysis_raw, submitted_by_phone
Invoice Drafts

GET  /invoices                      → list all
POST /invoices                      → internal — called by agent only
     Body: project_id, inspection_report_id, invoice_number,
           claim_percentage, claim_amount_myr
Purchase Orders

GET  /purchase-orders               → list all
POST /purchase-orders               → internal — called by agent only
     Body: project_id, vendor_id, po_number, item_description,
           quantity, unit_price_myr, total_price_myr
Vendors

GET  /vendors?region={region}       → list vendors, optionally filtered by region
Real-time Events (SSE)

GET  /events
Streams text/event-stream. Every time a new activity_log record is inserted (by any agent action), this endpoint broadcasts a JSON event to all connected frontend clients. Frontend subscribes on mount, updates the activity feed and dashboard counters without a page reload.

Event format:


{
  "event_type": "inspection_created",
  "description": "AI inspection report created for Greenfield Phase 1",
  "entity_type": "inspection_report",
  "entity_id": 12,
  "timestamp": "2026-06-18T09:41:22Z"
}
6. Agent Design
6a. Intent Router
Every incoming WhatsApp message first passes through the intent router before any LLM call:


if message has image attachments:
    → dispatch to INSPECTION AGENT

elif active session state == "awaiting_procurement_confirm":
    if message body is "yes" / "approve" / "ok" (case-insensitive):
        → dispatch to CONFIRMATION HANDLER
    elif message body is "no" / "cancel":
        → cancel session, reply "OK, cancelled."
    else:
        → reply "Please reply YES to confirm or NO to cancel."

elif message body contains procurement keywords
    (need, order, buy, procure, panels, materials, urgent, units, short):
    → dispatch to PROCUREMENT AGENT

else:
    → reply with a generic help message
No LLM call for the routing decision. Pure keyword + session state logic. Keeps routing fast and deterministic.

6b. Inspection Agent
Trigger: One or more image attachments received.

Step 1 — Download images
Twilio provides MediaUrl0, MediaUrl1, etc. with HTTP basic auth. Download each image using Twilio credentials. Store the raw bytes temporarily (in memory or to /tmp). Optionally re-upload to Cloudinary for a permanent URL; otherwise use the Twilio URL directly (they persist for a short time).

Step 2 — Vision LLM analysis per photo
Send each image to the vision LLM with this system prompt:

You are a solar installation site inspector. Analyze this construction site photo and return a JSON object with these fields:

panels_detected (integer): number of solar panels visible that appear to be installed
panels_with_issues (integer): count of panels that look misaligned, damaged, or incorrectly positioned
issues (array of strings): brief description of each issue spotted, e.g. "Panel in row 3 appears tilted"
notes (string): any other observations about the installation state
If the image does not clearly show solar panels, return panels_detected: 0.
Return only valid JSON. No markdown, no explanation.

Step 3 — Aggregate across photos
Sum panels_detected across photos but cap at project.total_panels (the photos may overlap or show the same panels from different angles). Use the maximum single-photo detection as the canonical count, not the sum. Average or take the maximum for issues. Combine all issue descriptions.

Step 4 — Project association
If the submitting phone number maps to exactly one active project → use it directly.
If ambiguous (more than one project for that region) → reply asking "Which project? Reply 1 or 2:" and store state as awaiting_project_selection. For the demo, seed the demo phone number as associated with Greenfield Phase 1 to avoid this branch during recording.

Step 5 — Calculate completion and invoice amount


completion_pct = (panels_detected / project.total_panels) × 100
claim_amount = project.contract_value × (completion_pct / 100)
invoice_number = "PC-" + year + "-" + zero-padded sequential number
Step 6 — Write to DB
Insert inspection_reports row → get its ID → insert invoice_drafts row → insert activity_log rows for both. The SSE endpoint will pick up the activity log inserts and push to the frontend immediately.

Step 7 — Reply via Twilio REST API
Send a WhatsApp message back to the submitting number:


Site Inspection Complete ✅

Project: {project.name}
📸 Photos analyzed: {count}
🔢 Panels detected: {panels_detected} of {project.total_panels}
⚠️ Issues flagged: {panels_with_issues}
📈 Completion: {completion_pct:.0f}%

Progress claim draft created:
Invoice {invoice_number}
Amount: RM {claim_amount:,.0f} ({completion_pct:.0f}% of RM {contract_value:,.0f})

View in portal → {FRONTEND_BASE_URL}/projects/{project.id}
6c. Procurement Agent
Trigger: Text message with procurement intent.

Step 1 — Extract procurement intent (LLM)
Send the user's message to the LLM with this prompt:

Extract procurement details from this message and return JSON:

item_description (string): what is being requested
quantity (integer): how many units, default 1 if unspecified
site_or_region (string): location mentioned, or null
urgency (string): "urgent", "normal", or "low"
deadline_hint (string): any date/timeframe mentioned, or null
Message: "{user_message}"
Return only valid JSON.

Step 2 — Vendor lookup
Query vendors table filtered by region matching site_or_region. If no region was extracted or no match, return all active vendors. Order by on_time_rate DESC for the first recommendation.

Step 3 — Acknowledge and signal RFQ dispatch
Immediately reply to the user:


Got it. Searching approved vendors for {region}... 🔍
Then:


RFQ sent to {count} vendors. Waiting for quotes...
This two-part reply makes the agent feel like it is actually doing work asynchronously.

Step 4 — Simulate quote (wait + LLM)
Wait 8–10 seconds (async sleep — do not block the webhook response). Then call the LLM to generate a realistic quote:

Generate a realistic supplier quote response as JSON:

vendor_name (string): use this vendor name exactly: {top_vendor.company_name}
item_description (string): {item_description}
quantity (integer): {quantity}
unit_price_myr (number): make it close to but slightly different from {top_vendor.unit_price_myr}, realistic variation ±5%
delivery_days (integer): 2–5 days depending on urgency {urgency}
notes (string): brief professional note from the vendor
Return only valid JSON.

This produces a realistic, slightly varied quote on each demo run.

Step 5 — Present quote and save pending state
Save the full pending PO details to conversation_sessions.context for the phone number. Set state = "awaiting_procurement_confirm". Reply:


📋 Best Quote Received

Vendor: {vendor_name}
Item: {item_description}
Qty: {quantity} units × RM {unit_price:.0f}
Total: RM {total:.0f}
Delivery: {delivery_days} days (on-time rate: {on_time_rate}%)

Approve this PO? Reply YES to confirm.
6d. Confirmation Handler
Trigger: Message is "YES" and session state is awaiting_procurement_confirm.

Load pending PO context from session. Insert purchase_orders row. Insert activity_log row. Reset session to idle. Reply:


✅ {po_number} Created

{vendor_name} has been notified.
Expected delivery: {today + delivery_days}

View PO → {FRONTEND_BASE_URL}/purchase-orders/{po.id}

8. Frontend Dashboard
Pages and Routes
/ — Dashboard

Header: "FieldBot Operations Portal"
4 summary cards: Active Projects / Inspections This Month / Invoices Pending / POs This Month
Live Activity Feed: scrolling list of the latest 20 activity log entries, newest on top, updating in real-time via SSE. Each entry shows an icon (camera for inspection, file for invoice, package for PO), description, and a relative timestamp ("just now", "2 minutes ago").
Visual emphasis: when a new event arrives via SSE, the new activity feed item slides in from the top with a subtle highlight animation. Dashboard counters increment live. This is the "wow" shot for the demo.
/projects — Projects List

Simple card grid: project name, client, site location, contract value, status badge.
/projects/:id — Project Detail

Project header: name, client, site, total panels, contract value
Three tabs: Inspections | Invoice Drafts | Purchase Orders
Inspections tab: list of inspection reports with thumbnail grid of photos, completion percentage bar, issues count, timestamp
Invoice Drafts tab: list with invoice number, claim amount, status badge
Purchase Orders tab: list with PO number, vendor, item, total, status
/purchase-orders — Purchase Orders List

Full list across all projects. Columns: PO number, project, vendor, item, qty, total, status, date.
Real-time (SSE)
Single useEffect on the Dashboard component opens an EventSource to GET /events. On each event: prepend to activity feed state array, update the relevant counter. Use a React key based on event ID to animate the new entry in. No polling — the SSE connection stays open for the duration of the demo.

Design Notes
Dark sidebar, clean white content area, green accent color (solar/nature association)
All numbers formatted as RM X,XXX for Malaysian Ringgit
Mobile-responsive is not required — demo will be recorded on desktop screen only
No authentication — this is a demo, open access is fine

Criteria for selection:

Shows panels in varying states: some rows complete, some partial (this makes the "partial completion" story credible)
At least one photo should have a small visible imperfection (a panel slightly off-angle, a gap in a row) for the AI to flag as an issue

If I just run it locally, is hosting really necessary? (you don't have to change the plan, just answer the question)
No.

For the demo video, local is fine. You control everything — the backend runs on localhost:8000, frontend on localhost:5173, and you screen-record both.

The only reason hosting matters is Twilio's webhook. Twilio needs a public HTTPS URL to POST incoming WhatsApp messages to your backend. Your local localhost is not reachable from Twilio's servers.

Fix: use ngrok (free tier). Run ngrok http 8000 and it gives you a public HTTPS URL like https://abc123.ngrok.io that tunnels to your local backend. Paste that into the Twilio sandbox webhook setting. Done.

So the full local setup is:

Backend: localhost:8000
Frontend: localhost:5173
ngrok tunnel → Twilio webhook
No Railway, no Render, no Vercel needed
One caveat: ngrok free tier URLs reset every time you restart ngrok, so you'd need to update the Twilio webhook URL each session. Not a problem for a demo recording — you set it once and keep everything running.
